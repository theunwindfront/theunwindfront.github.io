A Security Checklist for Frontend-Heavy Laravel Apps

Sagar Pansuriya · Dec 28, 2026 · 8 min read

You've probably seen a pull request like this. A Livewire component with a public $postId property, a delete() method that trusts it, and a Blade view that prints a product description with {!! !!} because "the editor outputs HTML". Everything works. The tests pass. And any logged-in user with DevTools open can delete someone else's records and inject a script into every product page.

Laravel gives you strong defaults: escaped output, CSRF protection, hashed passwords, prepared queries. The trouble in frontend-heavy apps is that we keep adding surfaces where those defaults don't reach. Alpine directives, Livewire actions, JSON dropped into scripts, file uploads, SPA auth. Each one is a place where the browser gets more power, and the browser is the one part of your system you don't control.

This is the checklist I walk through on Blade, Livewire and Alpine projects before they go live. It's not exhaustive, but it covers the mistakes I see most often in code review.

The rule underneath everything

Every value that comes from the browser is a suggestion. Form fields, hidden inputs, query strings, Livewire public properties, the arguments to a Livewire action, headers, file names, MIME types. All of it can be changed by anyone who opens DevTools or replays a request with curl.

So the server has to do four things on every request, in this order: limit how often it can happen, validate the shape of the data, authorize the action against the current user, and escape the output for the context it lands in. Most of the items below are one of those four, applied somewhere people forget.

1. XSS: know which Blade output you're using

{{ $value }} runs through htmlspecialchars, so it's safe for HTML text and quoted attribute values. {!! $value !!} prints raw HTML. Treat every {!! !!} in a codebase as a question that needs an answer in the PR: where does this string come from, and who sanitized it?

{{-- Safe: escaped --}}
<p>{{ $product->description }}</p>

{{-- Dangerous unless $html was sanitized on save with an allow-list --}}
<div class="prose">{!! $product->description_html !!}</div>

If you genuinely need user-authored rich text, sanitize it with a real HTML sanitizer using an allow-list of tags and attributes, ideally when you save it, and store the clean version. Regex-based stripping is not a sanitizer.

Escaping isn't enough for URLs

Blade escaping doesn't stop javascript: URLs. <a href="{{ $user->website }}"> is perfectly escaped and still runs a script if the value is javascript:alert(1). Validate URLs on input with the url rule and restrict the scheme to http and https.

Passing data into JavaScript: use @js

The classic mistake is echoing JSON into an Alpine attribute or a script tag by hand. HTML escaping and JavaScript escaping are different problems. Laravel's @js directive (backed by Illuminate\Support\Js) encodes a value so it's safe inside a JavaScript expression in an HTML attribute or script:

{{-- Fragile: a quote or </script> in the data can break out --}}
<div x-data="{ items: {!! json_encode($items) !!} }">

{{-- Better --}}
<div x-data="{ items: @js($items) }">

Alpine's x-html is {!! !!} in disguise

x-html sets innerHTML. If the value ever contains user input, you have XSS on the client side, and no amount of Blade escaping helps because the dangerous string is assembled in the browser. Default to x-text, and allow x-html only for content you generated or sanitized yourself. The same goes for innerHTML in any custom JavaScript.

2. Content Security Policy, with nonces from Vite

A CSP is your safety net for the XSS you didn't catch. A strict policy only runs scripts that carry a nonce generated for that response, so an injected <script> tag simply doesn't execute.

Laravel's Vite integration supports this directly. Call Vite::useCspNonce() in a middleware and the @vite directive adds the nonce to the tags it generates. Then send the header yourself:

// app/Http/Middleware/ContentSecurityPolicy.php
public function handle(Request $request, Closure $next): Response
{
    Vite::useCspNonce();

    $response = $next($request);
    $nonce = Vite::cspNonce();

    $response->headers->set('Content-Security-Policy', implode('; ', [
        "default-src 'self'",
        "script-src 'self' 'nonce-{$nonce}'",
        "style-src 'self' 'unsafe-inline'",
        "img-src 'self' data:",
        "object-src 'none'",
        "base-uri 'self'",
        "frame-ancestors 'self'",
    ]));

    return $response;
}

Use the same nonce on any inline script you write: <script nonce="{{ Vite::cspNonce() }}">.

Two honest caveats. First, Alpine's standard build evaluates directive expressions in a way that needs 'unsafe-eval'. Alpine publishes a separate CSP-friendly build with restrictions on what expressions can do, and Livewire's docs cover its current CSP options, so check both before you commit to a strict policy. Second, roll it out with Content-Security-Policy-Report-Only first. Third-party widgets will break, and you want to find out from reports, not from support tickets.

3. CSRF: Livewire, forms and SPAs

Blade forms need @csrf, and Laravel rejects state-changing requests without a valid token. Livewire sends the token with its own requests, so you rarely think about it there. The places it goes wrong:

  • Custom fetch calls. Send the token in an X-CSRF-TOKEN header, read from <meta name="csrf-token" content="{{ csrf_token() }}">.
  • SPAs with Sanctum. Use cookie-based SPA authentication: request /sanctum/csrf-cookie first, then let your HTTP client send the X-XSRF-TOKEN header from the XSRF-TOKEN cookie. Configure your stateful domains properly rather than disabling checks until it works.
  • Over-broad exceptions. Excluding a webhook route from CSRF is normal. Excluding api/* on a session-authenticated app is not. Keep the exception list short and specific, and verify webhook signatures instead.
  • GET routes that change state. CSRF protection doesn't cover GET. A "delete" link that uses GET is deletable by an image tag on another site.

4. Mass assignment: validate, then fill

The unsafe pattern is short enough to slip through review:

// Anyone can add is_admin=1 to the request
$user->update($request->all());

// Only fields that passed validation
$user->update($request->validated());

Keep $fillable tight on models, prefer validated() or safe()->only([...]) over all(), and never set $guarded = [] on a model that user input touches. In local development, Model::preventSilentlyDiscardingAttributes() turns quietly ignored attributes into exceptions, which catches mismatches between forms and $fillable early.

In Livewire, the same applies: call $this->validate() and fill models from what it returns, not from every public property. If you're using form objects, I covered the patterns in Livewire form objects and validation.

5. Livewire actions are public endpoints

This is the one that catches experienced Laravel developers. Every public method on a Livewire component can be called from the browser, with any arguments. Every public property can be changed. A hidden input or a disabled button is UI, not security.

// Vulnerable: trusts the client for both identity and permission
public int $postId;

public function delete(): void
{
    Post::find($this->postId)->delete();
}
use Livewire\Attributes\Locked;

#[Locked]
public int $postId;

public function delete(): void
{
    $post = Post::findOrFail($this->postId);

    $this->authorize('delete', $post);

    $post->delete();
}

#[Locked] stops the client from changing the property, which is useful for IDs. But the real fix is the authorize() call against a policy, inside the action, every time. Locking a property tells you the ID hasn't been tampered with. It doesn't tell you this user is allowed to delete that post.

The same goes for action arguments. wire:click="delete({{ $post->id }})" is fine only if delete($id) loads the post and authorizes it. Also scope queries to the user where it makes sense ($request->user()->posts()->findOrFail($id)), so a missing policy check fails closed.

6. Rate limiting beyond the login form

Laravel's starter kits rate-limit login. Frontend-heavy apps have many more endpoints worth protecting: search, contact forms, "resend code", anything that sends email or costs money (like an AI call). Define named limiters and attach them to routes:

// AppServiceProvider::boot()
RateLimiter::for('contact', function (Request $request) {
    return Limit::perMinute(3)->by($request->user()?->id ?: $request->ip());
});

// routes/web.php
Route::post('/contact', ContactController::class)->middleware('throttle:contact');

Livewire actions don't go through your route middleware individually, so rate-limit inside the action:

public function send(): void
{
    $key = 'contact:'.(auth()->id() ?? request()->ip());

    if (RateLimiter::tooManyAttempts($key, 3)) {
        $this->addError('form', 'Too many attempts. Try again in a minute.');
        return;
    }

    RateLimiter::hit($key, 60);
    // ...
}

7. File uploads: trust nothing about the file

The file name, extension and client-reported MIME type are all user input. A safe upload path looks like this:

  • Validate type and size on the server: 'avatar' => ['required', 'image', 'max:2048'], or mimes:pdf,docx for documents. max is in kilobytes.
  • Don't accept SVG from users unless you sanitize it. SVG is XML that can contain scripts.
  • Store with a generated name ($file->store('avatars') does this) instead of the original file name.
  • Keep private files off the public disk and serve them through a controller that authorizes the request.
  • With Livewire's WithFileUploads, validate in your save action as well. The temporary upload rules in config are a coarse outer limit, not your validation.

8. Security headers

A small middleware that adds a handful of headers to every response is cheap insurance:

HeaderTypical valueWhat it prevents
Strict-Transport-Securitymax-age=31536000; includeSubDomainsDowngrades to HTTP
X-Content-Type-OptionsnosniffBrowsers guessing a file is a script
Referrer-Policystrict-origin-when-cross-originLeaking full URLs to other sites
Permissions-Policycamera=(), microphone=(), geolocation=()Features you don't use being abused
CSP frame-ancestors'self'Clickjacking via iframes

Only enable HSTS once HTTPS works everywhere on the domain, including subdomains if you add includeSubDomains. It's hard to undo.

And the boring ones that still bite: APP_DEBUG=false in production, .env never in the web root or the repo, and secure, httpOnly session cookies. If you ship desktop apps too, the threat model changes again; see securing NativePHP apps.

The checklist

  1. Every {!! !!} has a documented source and a sanitizer behind it.
  2. User-supplied URLs are validated and limited to http/https.
  3. Data passed to Alpine or scripts uses @js, never hand-rolled json_encode.
  4. x-html and innerHTML never receive user input.
  5. A CSP with Vite nonces, rolled out in report-only mode first.
  6. Custom fetch calls send the CSRF token; exceptions are few and specific; no state-changing GETs.
  7. Models are filled from validated(), never all().
  8. Every Livewire action that touches data calls authorize(); IDs are #[Locked].
  9. Anything that sends email, costs money or searches is rate-limited, including Livewire actions.
  10. Uploads are validated server-side, renamed, and private files are served through authorization.
  11. Security headers are set, debug is off, secrets stay out of the repo.

None of these are hard. What makes them easy to miss is that the app works perfectly without them. That's why they belong on a checklist and in your PR template, not in someone's memory.
